# RestockIQ: Flutter Frontend (APP) Development Guide

Welcome to the **Frontend Module** of RestockIQ! This document is the master roadmap specifically for the UI/UX developers on the team. 

Our goal is to build a cross-platform mobile app (using Flutter) targeted at **non-technical cafe and bakery owners**. The UI must be frictionless, hiding all the complex Prophet/XGBoost Machine Learning math behind simple, actionable screens.

---

## 🛠 Tech Stack & Rules
*   **Framework:** Flutter (Dart)
*   **Target Devices:** iOS & Android (Mobile First)
*   **Backend Connection:** Will consume a FastAPI (Python) backend via REST.
*   **Golden Rule of the UI:** The user should never have to guess what a number means. The app tells them *exactly* what to do (e.g., "Order 15 Croissants") using plain-language explanations.

---

## 🎨 Design System: "Warm Tech" (Stitch Integration)

The frontend must strictly adhere to the **RestockIQ Mobile UI Design** system currently housed in our Stitch project.

*   **Aesthetic:** "Warm Tech" – Merges the precision of AI-powered forecasting with the tactile, inviting atmosphere of a neighborhood bakery. It minimizes cognitive load and "math anxiety".
*   **Colors:**
    *   **Base:** Off-white cream (`#fcf9f4`) to reduce screen glare in bright kitchens.
    *   **Primary:** Deep Forest Green (`#1b4332`, `#012d1d`) for core branding and primary actions.
    *   **Secondary:** Soft Amber (`#ffb702`) for "Learning" states (AI is processing data).
    *   **Tertiary:** Warm Coral (`#ff8080`) for "Waste Risk" alerts.
*   **Typography:** **Montserrat** for high-impact numbers/headers (e.g., forecasted quantities) and **Inter** for highly readable body text.
*   **Geometry & Depth:** 
    *   Soft, approachable shapes (16px/24px corner radii on cards, pill-shaped primary buttons).
    *   Ambient, tinted shadows (e.g., green-tinted 5% opacity shadows on cards to avoid industrial grey).
    *   Oversized touch targets (48px minimum) for fast-paced, high-stress kitchen environments.

## 🚀 Development Roadmap: The 7 Core Screens

This is the exact sequence in which the UI should be built, using the Stitch screens as the source of truth. **Do not skip Item Setup (Screen 2)**, as the entire Machine Learning backend will crash if items are not defined first!

### 1. Login & Authentication Screen
*   **Function:** Standard email/password login (connected to Firebase Auth).
*   **Role-Based UI:** The app must support 2 roles (Owner vs. Manager/Employee).
*   *Requirement:* Only the Owner role can see the "Manage Staff" section in Settings.

### 2. Item Setup Screen (CRITICAL DEPENDENCY)
*   **Function:** A form to add/edit menu items.
*   **Critical Fields:** Item Name, Category, Price, and a **Perishable vs. Non-Perishable Toggle**.
*   **UI Component:** Input fields use a 2px muted forest green border on focus.
*   *Why it matters:* If the UI does not capture whether an item is perishable, the backend ML Waste Action Engine cannot function.

### 3. The Main Dashboard (Home Screen)
*   **Function:** The first thing the owner sees in the morning.
*   **Components:**
    *   **LLM Daily Summary:** A card at the top displaying a plain-language summary generated by the AI.
    *   **Today's Restock List:** Inventory Cards (white background, 16px radius, soft green-tinted shadow) with the forecasted number positioned top-right in `Montserrat` display-quantity style.
    *   **Cold-Start Badges:** Status Chips showing "Learning your patterns ⏳ Day 5/14" (Soft Amber).

### 4. End-of-Day Inventory Input Screen
*   **Function:** Where the staff logs what didn't sell at closing time.
*   **Smart Pre-fill:** Automatically pre-fill the "Leftover" box with the system's calculated guess.
*   **Quantity Adjuster Component:** A large, tactile component with oversized +/- buttons to allow for quick manual overrides of AI suggestions.
*   **Perishable Rule:** If an item is marked as Perishable, the leftover input box is locked and auto-resets to 0.

### 5. Item Detail & Forecast View
*   **Function:** When a user taps an item on the Dashboard, this screen slides up.
*   **Components:**
    *   **The Math Explained:** Visual restock formula: `[Predicted Demand] + [Safety Stock] - [Current Stock] = [Restock Qty]`.
    *   **Progress Bars:** Soft, rounded tracks (8px height) using status colors to show "Stock Level vs. Forecasted Need."
    *   **Narrator Explanation:** Text block where the LLM explains *why* the demand is high.

### 6. Waste Action Alerts
*   **Function:** Intraday alerts for slow-moving stock.
*   **Components:** High-visibility cards in **Warm Coral** that flag an item.
*   *Example UI:* "Warning: Croissants are selling very slowly. Action Recommended: Apply a 20% discount now to clear inventory."

### 7. Settings & Management
*   **Function:** Basic app management.
*   **Components:** Manage menu items, Notification toggles, and Staff Management (strictly locked to the Owner role).

We will be utilizing the Stitch UI generator to scaffold these screens in Flutter. Ensure that all generated components map perfectly to the "Warm Tech" design tokens defined above.

*   **Auth & Database:** **MongoDB** is the single, master database for the entire project. It stores everything: user credentials, roles, items, daily sales, and pre-computed forecasts. FastAPI handles all JWT authentication directly. There is no Firebase.
*   **Backend API:** **Python FastAPI**. It acts as the bridge for our Machine Learning and Database. FastAPI will read daily sales from MongoDB, run the models (via the batch job), and serve the forecasted results from MongoDB.
*   **UI Scaffolding:** **Stitch MCP**.

## 📂 Codebase Architecture & Directory Analysis (`lib/`)

The Flutter frontend codebase is highly organized into a modular, feature-based architecture, utilizing the `Provider` pattern for state management. Here is a detailed breakdown of what currently exists in the `lib/` directory:

### 1. `models/` (Data Structures)
This folder defines the strongly-typed Dart classes that map directly to our MongoDB/FastAPI schemas.
*   **`inventory_item.dart`**: The core model for bakery items, tracking `isPerishable`, current stock, category, and `unit` (e.g., LBS vs Units).
*   **`stock_check_entry.dart`**: Models the end-of-day leftover counts.
*   **`waste_alert.dart`**: Defines the structure for intraday waste warnings (e.g., triggering a 20% discount on slow-moving perishable items).

### 2. `providers/` (State Management)
We use the `provider` package to manage app state globally and decouple business logic from the UI. 
*   **`inventory_provider.dart`**: Manages the list of items and their forecasts. Currently holding mock data, this provider will be the one responsible for making HTTP GET/POST calls to the FastAPI `items` and `forecasts` endpoints.
*   **`stock_check_provider.dart`**: Handles the logic for the end-of-day inventory submission (pushing actual leftovers vs expected leftovers).
*   **`waste_alerts_provider.dart`**: Listens for and manages the list of active markdown alerts.

### 3. `screens/` (UI Views)
The 7 core screens mapped out in our roadmap are physically located here:
*   `login_screen.dart` & `forgot_password_screen.dart`: The entry point (soon to be wired to FastAPI JWT auth).
*   `dashboard_screen.dart` / `dashboard_placeholder_screen.dart`: The primary morning view showing the daily forecast summary.
*   `item_setup_screen.dart`: The critical form for adding new inventory items and defining perishability.
*   `inventory_checkin_screen.dart`: The closing time view for logging leftover stock.
*   `item_detail_forecast_screen.dart`: The deep-dive view explaining the math behind a specific item's restock suggestion.
*   `waste_alerts_screen.dart`: The intraday view for markdown notifications.
*   `settings_screen.dart`: Role-based management screen.

### 4. `widgets/` (Reusable UI Components)
Highly modular components built using the "Warm Tech" design system.
*   `dashboard_forecast_card.dart`, `inventory_item_card.dart`, `waste_alert_card.dart`, `stock_check_card.dart`: Custom styled cards with specific soft shadowing and border radii.
*   `quantity_adjuster.dart`: The oversized, tactile +/- button component for rapid kitchen input.
*   `sales_forecast_chart.dart`: Visual representation of historical vs predicted sales.
*   `primary_button.dart`, `custom_input.dart`, `custom_dropdown.dart`: Foundational form elements.
*   `bottom_nav_bar.dart` & `dotted_background.dart`: Scaffold components for layout.

### 5. `theme/` (Design Tokens)
*   `app_theme.dart`, `app_colors.dart`, `app_typography.dart`: This is where the exact hex codes (e.g., `#1b4332`, `#ffb702`) and font families (Montserrat, Inter) from the Stitch design system are centralized and applied globally.

**Current Context:** The entire UI skeleton is fully scaffolded and built. The UI currently relies on the mock data stored inside the `providers/`. The immediate next step for the frontend is replacing the hardcoded data in those providers with real `http` calls to our new production FastAPI backend.

## 🏃 Parallel Development Plan (3 Phases)

To ensure Frontend and Backend don't block each other, follow this phased approach:

### Phase 1: The Foundation (Mock Data)
*   **Frontend:** Build the App Shell, Navigation, and the **Item Setup Screen**. *This is critical so we can define items as Perishable vs Non-Perishable.*
*   **Backend:** Set up the MongoDB collections and FastAPI routes. **DO NOT** run ML models yet. Serve "fake" hardcoded JSON forecasts so the frontend can build the UI visually.

### Phase 2: The Core ML Loop
*   **Frontend:** Build the **Main Dashboard** and the **End-of-Day Input** screen using the Stitch design system.
*   **Backend:** Integrate the Prophet + pooled HistGradientBoostingRegressor (for primary items) and the TSB + category-prior engine (for sparse items) into a nightly Python batch job. Read the real items from MongoDB, run the predictions, and serve the actual raw forecasted numbers. 

### Phase 3: The "Brain" (LLM Polish)
*   **Frontend:** Build the **Waste Action Alerts** and display the LLM text summaries.
*   **Backend:** Integrate the OpenAI/Gemini API to analyze the Prophet forecasts and generate plain-text advice (e.g., "Order 15 extra croissants due to rain").
